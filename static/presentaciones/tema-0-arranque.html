02 · MULTAGAL

Reglas de negocio (I)

R1

Pronto pago

Bonificación del 50% si se paga en 20 días naturales tras la notificación, con renuncia a alegar.

R2

Firmeza

La detracción de puntos sólo se materializa con resolución firme.

R3

Saldo cero

El caso transaccional del curso. Actualizar el saldo y suspender el permiso deben ser atómicos.

R3 se reimplementa en JDBC, luego en JPA y se compara después: la misma operación resuelta con tecnologías distintas.
02 · MULTAGAL

Reglas de negocio (II)

R4

Prescripción

3 meses (leves) o 6 (graves/muy graves) sin notificar.

R5

Alegaciones pendientes

No se resuelve un expediente con alegaciones pendientes de contestar.

R6

Identificar al conductor

Obligatorio para el titular; su omisión genera otra infracción autónoma muy grave.

06 · IoC e inyección de dependencias

El problema: acoplamiento

código que NO escribiremos
public class ServicioExpedientes { private final RepositorioExpedientesJdbc repo = new RepositorioExpedientesJdbc( "jdbc:mariadb://localhost:3306/multagal"); }
  • ✗
    Atado a JDBC. Migrar a JPA obliga a editar esta clase.
  • ✗
    No se puede probar sin una MariaDB arrancada.
  • ✗
    Configuración dentro del código. Viola la condición formal.
  • ✗
    Gestiona un ciclo de vida que no le corresponde.
06 · IoC e inyección de dependencias

La solución: invertir el control

ServicioExpedientes.java
@Service public class ServicioExpedientes { private final RepositorioExpedientes repo; // interfaz public ServicioExpedientes( RepositorioExpedientes repo) { this.repo = repo; } }
  • ✓
    Depende de la interfaz. Cambiar de tecnología no toca esta clase.
  • ✓
    Se puede probar con un mock, sin base de datos.
  • ✓
    La URL vive en application.yml.
DI es un patrón de diseño, no magia de Spring: funciona igual con un simple new ServicioExpedientes(new RepositorioJdbc(...)). Spring sólo automatiza el cableado.

06 · IoC e inyección de dependencias

Los estereotipos

AnotaciónCapaQué añade

06 · IoC e inyección de dependencias

Por constructor, nunca por campo

Correcta

Por constructor

Campos final, inmutable y seguro entre hilos. Imposible construir sin dependencias. Se instancia en test sin contenedor.

Prohibida en el módulo

@Autowired en campo

No puede ser final, oculta dependencias, y en un test unitario puro el campo queda a null.

Con Lombok: @RequiredArgsConstructor genera el constructor con los campos final — equivalente, siempre que sepas explicar qué genera.
06 · IoC e inyección de dependencias

Cuando hay varias implementaciones

@Primary

Una implementación es la predeterminada entre varias candidatas.

@Qualifier

Se elige explícitamente en el punto de inyección.

La interesante

@ConditionalOnProperty

Se elige por configuración, editando una línea de application.yml, sin recompilar.

Con ambos repositorios registrados sin resolver la ambigüedad: NoUniqueBeanDefinitionException: expected single matching bean but found 2.
06 · IoC e inyección de dependencias

Singletons sin estado mutable

ServicioMal.java
@Service public class ServicioMal { private Expediente actual; // NO!!! public void procesar(Expediente e) { this.actual = e; // carrera } }
Condición de carrera garantizada

Un @Service es singleton

La misma instancia atiende peticiones concurrentes. Sus campos deben ser final y contener sólo dependencias o configuración inmutable.

07 · Controladores REST y validación

El DTO de entrada

NuevoExpedienteRequest.java
public record NuevoExpedienteRequest( @NotBlank String numero, @NotNull @DecimalMin("0.0") BigDecimal importe, @Pattern(regexp = "\\d{4}[A-Z]{3}") String matricula ) { }
DTO ≠ entidad

Frontera de la API

El cliente nunca debe rellenar un id generado o un estado que decide el servicio. Separar DTO y dominio evita que cambios en la API obliguen a tocar el modelo de negocio.

07 · Controladores REST y validación

El controlador y @Valid

ExpedientesController.java
@RestController @RequestMapping("/api/expedientes") public class ExpedientesController { @PostMapping @ResponseStatus(HttpStatus.CREATED) public ExpedienteResponse crear( @Valid @RequestBody NuevoExpedienteRequest p) { ... } }
Error más común

Sin @Valid, nada se evalúa

@NotBlank, @NotNull o @Pattern son sólo metadatos hasta que algo las evalúa. El código compila y el IDE no avisa.

07 · Controladores REST y validación

Qué NO va en el DTO

PreguntaDónde se resuelve
¿Formato/tamaño/rango correcto?DTO, con Bean Validation
¿Existe ya ese DNI / número de expediente?service, consultando el repositorio
¿Coherente con saldo, estado, plazos?service
¿Depende de una regla del dominio (R1...)?service
@Valid se resuelve antes de tocar la base de datos ni ningún otro bean: sólo comprueba el dato aislado, nunca su significado en el dominio.
